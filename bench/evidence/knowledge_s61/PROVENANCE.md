# knowledge_s61 —— ★7z 多样性取证（第五十八轮）：**只读诊断，内核一字未改**

证据 `probe_7z.py` / `probe_7z.txt`（零模型，跑 99 个归档 cap）。

## 起因

第五十七轮（7y）留下：**354 次交付 = 28 份互异答案**。当时只登记没解释。
这一轮把它拆成三个可判的问句 —— 因为**不同答案指向完全不同的下一步**：

| 情形 | 瓶颈在 | 该动的地方 |
|---|---|---|
| 请求种类少 + 同请求回答一致 | **内核**（要得少、问得一样） | 候选生成 |
| 请求种类多 + 回答仍窄 | **模型**（对提示变化不敏感） | 换能力/换题，动提示没用 |
| 同请求体也会翻面 | **解码**（T=0 不确定） | 采样政策 → 且之前的"极差 0"要重读 |

## 读数

**Q0 传输层（1586 次请求，逐条数字段）**

| 字段 | 值 |
|---|---|
| `temperature` | **0.0**（1586/1586，无一例外） |
| `n` | **从未出现**（1586/1586 absent） |
| 请求体字段组合 | 永远只有 `max_tokens / messages / model / temperature` |

⇒ `planner.propose(n=…)` 里的 n>1 **不是 API 层采样**：它在源码注释里写着
"产出 n 个候选步骤…n>1 就是 test-time compute 的落点"，实际实现是"**在同一份贪心输出里
请模型写出 n 个候选**" —— 声明与实现不一致（第二十一轮 `verify` 同型的"声明了没有"）。
⛔ 未实施修复，只登记。

**Q1 请求多样性 vs 答案多样性**

| 通道 | 去重请求体 | 去重响应 | 响应/请求 |
|---|---|---|---|
| 答案通道 `answer()` | 152 | **30** | 0.20 |
| 规划通道 `propose()` | 64 | **45** | 0.70 |

（答案通道：g7d2 18→6 / g7d3 26→8 / g7e1 37→6 / g7e2 71→10）

⇒ **多个不同的请求塌缩到同一份答案**：152 种问法只得到 30 种回答。
规划通道的塌缩轻得多（0.70）⇒ 塌缩发生在"把东西写成最终答案"这一步，不是规划那一步。
这与此前"结果层 `$[$]` vs `s[-(n-3):]`"的过程证据同向：不是想不到，是**最后那一笔**写不准。

**Q2 确定性（同请求体重复问）**

    147 个重复请求体 ⇒ 1 种回答 ×146、2 种回答 ×1
    同请求得到完全相同回答的比例 = **99.3%**（唯一例外在 answer 通道 g7e2）

⇒ **同请求体几乎完全确定** ⇒ ⛔ 修正旧登记：过去写"T=0 不保证跨请求确定性
（同字节请求体跨时刻可翻）"，这句话要加量化：**实测只有 1/147 ≈ 0.7% 翻面**。
⛔ 边界：那是这台机 + 这个 ollama + 这个模型的读数，不许跨环境外推。

## 判读（谨慎版）

满足 **Q1 少 + Q2≈1**，且"响应/请求"只有 0.20：
⇒ **多样性受限于"内核向模型提出了多少种不同的问题"**。T=0 下每多一种问法至多多一份答案，
而 25 类臂十六个窗口总共也只问出 ~38 种问法/题。

⛔ **不许**顺势推"那就多采样几次"：
7y 已证明题面派生的判据**不具备选择能力**，而自评这条解被契约 AG（外部评审：只读 /
防自评 / 防跨口径）明令禁止 ⇒ **多生成出来的候选没有可用的选择器**。
在没有选择器之前开采样臂，只能得到"答案更多 + 无法从中挑" ⇒ 预期收益为零。

## 去向（登记，本轮不实施）

至此本套题已连四轮负结果（7v-e / 7w / 7x / 7y），而本轮把 7y 那个"答案集合只有 ~7 个"
的读数解释清楚了：**窄，是因为内核能问出的问法就那么几种**（T=0 ⇒ 一问一答，152 问 → 30 答）。
顺着方向 ② 往下走的正确顺序是：

    ① 候选生产率（多采样）→ ② **选择器** → ③ 才有选型红利

而 ② 恰恰是 7y 判死的那个东西 ⇒ **在没有新的选择器来源之前，方向 ② 不可执行**。

⇒ 本轮就此收口，转去做不受此瓶颈影响的产品化工作。等用户拍板：
换题族（①），还是先回答"选择器从哪来"（②-b，可能需要一个**真正外部**的信号渠道）。
