## 3. ⭐ 本轮真正的新读数：`=5` 的生效条件比 V77 说的窄

P5 不成立不是小数点问题，它把 `=5` 的接线缺口暴露出来了。两条路径的日志逐字对比如下。

### 3.1 `t04`（`=5` 生效 1 次 → 分数 1.0）

```

    ↪ 交付被打回 ⇒ 让位给候选 2/2
    ↪ 让位救回一个**步骤**：recall           ← 成功 ⇒ consecutive_failures 清零
↻ 打回报文进下一轮提问（让位成功也没把它冲掉）

    ✎ 重写的答案与被打回那版**不同**
    ✅ 打回之后的重写**过了闸**

```

### 3.2 `g7t4`（`=5` 一次都没进去 → 分数 0.0）

### 3.3 缺口在代码里的位置

```
core.py:1301   if consecutive_failures and last_error:
                   plan = self.planner.replan(...)          ← 打回后的第一次重规划走这里
core.py:1327   elif _carry:
                   ...
core.py:1401       if _rc == 5:
                       _rewrite = self.planner.answer(goal, clean=True)   ← `=5` 只在这个分支里
```

打回时 `_gate_finish` 返回 `ToolResult(False, error=_err)` ⇒ 主循环把它计成
`consecutive_failures += 1`、`last_error = _err` ⇒ **下一轮必然命中 `if` 分支**
⇒ `elif _carry:`（`=5` 的家）**进不去**。

⇒ **`=5` 只在「打回后让位救回一个成功步骤」的格上生效**。
- `t04`：候选宽度 2，让位给 `recall` 成功 ⇒ 清零 ⇒ 进 `elif` ⇒ `=5` ✅
- `g7t4`：候选只有 1 个 ⇒ 没得让位 ⇒ 停在 `if` ⇒ `=5` ❌
- `z02`：第 1 次打回让位成功 ⇒ `=5` 生效 1 次（产出 445 字符，**仍是 f-string 反斜杠**）；
  第 2 次打回没人让位 ⇒ 回 `if` 分支 ⇒ 第 3 次超限交付（`verify_retries=2`）

### 3.4 这条缺口同时改写了 V77 的读法

V77 的「6 题 × 6 跑，C3 `t04` 0.3333×6 → 1.0×6」：

- 那 6 题里**只有 `t04` 打回过**（V77 §2 表：其余五题 A 臂全 1.0）；
- `t04` 恰好是「让位成功」的那一格。

⇒ **V77 的 n 是 1 格，不是 6 格**（纪律 225/245：不同输入→同一产出 ⇒ n=1）。
它的 6 跑只证明「这一格的这个效应可复现」，**没有测到「让位失败」那条路**。
