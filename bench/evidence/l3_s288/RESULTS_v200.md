## 3. 三档投喂的实际差别

| 档 | served | 每题行数（4 个迭代步） | 首行是谁 |
|---|---|---|---|
| `off` | 0 | 0 | — |
| `prev` | 120（24 次筛 × 5） | 3 / 3 / 3 / 3 | `t04_merge_ranges`（字典序尾三） |
| `prev-self` | **144**（24 × 6） | 3 / 3 / 3 / 3 | **本题**（6/6） |
| `all` | 120 | 3 / 3 / 3 / 3 | 同 `prev`（轮内无人写账本） |

⭐ **`prev-self` 只换内容不换行数**：`pick = [self_c[-1]] + others[-2:]`
⇒ 自评占掉一格、挤掉一条别人的评审。**没有变宽，只是换人。**

### 3.1 ⭐⭐ 收尾那一版 prompt **一行评审都没有**

逐题 5 次 `_state()`，行数 `[3, 3, 3, 3, **0**]`，字符数如 `[356, 535, 772, 856, **712**]`。
第 5 次就是**收尾快照**：`_close_out` 里 `self._state(goal, history, _co_it)`
（`core.py:2816`）**不传 `task_id`/`scorer_sha`/`suite_sha`** ⇒
`_admissible_critiques` 在 `core.py:2030` 首个分支直接 `return []`。

而本轮 **6/6 题的最终交付都来自「收尾调用」**（`closeout.triggered=1`、
`origin={'收尾调用': 1}`）。
⇒ **评审块缺席的位置，正好是写最终答案的那一次调用。**
这不是「通道关着」，是「通道在关键那一步自己关了」。

## 4. 那 3 行长什么样（去重后只有 4 条）

```
[coding_small/t03_commas] 1.00 — 通过 5/5
[coding_small/t04_merge_ranges] 0.33 — 通过 2/6；失败: assert merge_ranges([(1,3),(2,6),(8,10)]) == [(1,6),(8,10)] ⇒ TypeError: 'tuple' object do…
[coding_small/t05_top_k] 1.00 — 通过 4/4
[coding_small/t06_rle] 1.00 — 通过 5/5
```

**两个口径，两个数，都报：**

- **严格口径**（预注册 §1：`why` 非纯通过语、且不含 assert 期望值 ⇒ 才计知识）：
  **0 行**。理由：含期望值的那条就是**答案**（V197 已判死「诊断是答案」）。
- **宽松口径**（只排除「通过 N/N」）：**5/18 = 27.8%**，去重后 **1/4**。
- ⭐ 两个口径的差**全部落在 t04 那一条**上：它同时含
  (a) 本题的期望值 `[(1,6),(8,10)]` —— 是答案；
  (b) `TypeError: 'tuple' object does not support item assignment` —— 这条**是可迁移的**。
  ⇒ **登记为口径未定，不选边**（⛔ 不许事后挑一个好看的数写进结论）。

## 5. 判决

1. **critique 通道是通的，但它的载荷形状决定了它传不了知识。**
   288 条 → 33 可达 → 5 可投 → **3 行**可读；3 行里 72% 是「通过 N/N」，
   剩下的是**别的题**的失败断言。上限不是通道宽度，是 `as_line()` 的**渲染形状**。
2. ⭐ **`answer` 字段 288 条全都存着，一条都进不了 prompt**（P3=0）：
   `as_line()` 不渲染它。账本存的与 prompt 读的**不是同一个东西**。
3. ⭐⭐ **收尾调用拿不到评审**（§3.1）：写最终答案的那一版 prompt 是全场
   上下文**最少**的一版。这条与 V199「累积可用 1/3059」是同一台机器上的两处漏水。
4. **`prev-self` 与 `prev` 是同一把宽度**（都 3 行），差的只是「自评 vs 别人」。
   ⇒ 「自省」这一环即使通电，也只有 **1 格**（自己那条），且内容是上次的失败断言。
5. ⚠️ **`rejected` 计数器归因不可信**：闸序 `self → cross_scorer`，
   别的套件里**同 id** 的行会先被记成 `self`。实测累计 `self=124`，
   而真正的自评拒绝只有 **24**（=24 次筛 × 1）。⇒ 这正是它文档里想避免的
   「分项计数无法归因」，只是漏在**顺序**上。

## 6. 自踩 6 条

1. **⛔ P1 押错**（押 0 得 33）：把「会换口径」当成「已经换了」。
   押「不可能发生」和押「发生」一样需要取证（纪律 3 的镜像）。
2. **⛔ 末步取样错**：第一版取 `steps[-1]` 当「下发的那版」⇒ 全部 0 行。
   真值是 `[3,3,3,3,0]` 的最后一步是**收尾快照**。
   ⇒ 「最后一个」≠「生效的那个」，要按**语义**选样。这个错反而挖出了 §3.1。
3. **⛔ 闸分解遍历 bug**：`for t, pair in keys_by_tid.items()` 把 `list` 当 `pair`
   ⇒ 288 个键只数了 75。**正例对照（每行合计=288）**逮住 —— 没有这个对照就会写出
   「cross_scorer=74」这种一看就假、但表面自洽的数。
4. **⛔ `rejected` 当成了分项计数**：它是**按闸序的首次命中**，不是互斥分类（§5.5）。
5. **⛔ `served/calls` 不能当「每次几条」**：`calls=30` 里 6 次是签名不全的提前返回
   （收尾/无 task_id），真实筛了 **24** 次。分母混了两类调用。
6. **⛔⛔ 第一次「真入口」跑出来的是 oracle，不是内核**：`--bench --offline` 下
   `use_llm=False` ⇒ 走参照点，日志里 `投喂=0` 是**内核没跑**，不是通道关。
   差一点把参照点的 0 读成「通道投喂 0」。⇒ 报「投喂量」前必须先证**内核跑过**。

## 7. 作用域（⛔ 越界即作废）

StubLLM × `coding_small`（6 题）× 单轮 × **空 state 目录**（把 `facts`/`episodes`
两条通道清零，剩下的跨题内容只有 critique）× 部署默认（`raw` 模式、`state_chars` 默认）。
⛔ 不覆盖真模型（真模型下收尾/重规划步数不同，行数会变）、
⛔ 不覆盖 `memory_mode=abstract`、⛔ 不覆盖跨套件累计、
⛔ 不覆盖「评审有没有让分数变好」（那要付判分，另起一轮）。

## 8. 下一刀（交用户）

① **量「把 `answer` 或题目摘要放进 `as_line()`」的收益** —— 本轮证明账本存着 288 份答案
   却一条都不渲染；这是通道内**唯一**还没试过的载荷改造（要改内核渲染，需用户拍板）。
② **修收尾 state 的签名缺口**（`core.py:2816` 不传三件套 ⇒ 最终交付那版无评审）——
   这是**接线缺损**，不是设计选择；改它只影响「收尾那一次看到什么」。
③ 判 `rejected` 的闸序该不该改成先比 sha 再比 self（§5.5 的归因错）。
