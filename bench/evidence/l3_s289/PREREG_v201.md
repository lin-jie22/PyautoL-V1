# V201 预注册：补齐收尾签名后，评审块**加得进去吗**（写于任何新读数之前）

V200 证了两件事：评审通道能到 prompt（每题 3 行），但**收尾那版 prompt 一行都没有**
（`core.py:2816` 不传 `task_id`/`scorer_sha`/`suite_sha`），而 6/6 题的最终交付来自收尾调用。

V200 §8② 说「修这个签名缺口」。⛔ 但**修之前必须先量**（V194 的价）：
如果补上签名后那 3 行被 `state_chars` 裁掉、或挤掉了别的块，修了也是白修。

本轮只问一件事：

> **把签名补齐，收尾那版 prompt 会不会净增 3 行评审？代价是什么？**

⛔ 不改内核（只在装置进程内包一层 `_state` 记录入参 + 用**同一实现**重算一次）。
⛔ 不造新装置种类（仍是 StubLLM + 真 `Core` + 复用 `run.py:_critique_snapshot`）。
⛔ 不判「有没有用」（那要付判分，另起一轮）。

---

## 1. 押注（五条，逐条可判）

| 号 | 押 | 依据（写在押之前） |
|---|---|---|
| **P1** | 收尾 state 缺的块**不止** `[外部评审]`：至少还缺 1 个（`[轨迹]` 或 `[工作记忆]`） | V200 实测收尾 712 字符 < 最后一次迭代 856 字符；若只缺评审那 3 行（≤150 字符），差值应 ≈150，而实测差 **144**——刚好卡在边界，必须逐块看才分得清 |
| **P2** | 补齐签名后，评审块**加得进去**（净增 3 行，且 `state_trimmed` 不增） | 收尾 state ≈712 字符，若 `cap` 明显更大就没有裁剪压力。**押「加得进」** |
| **P3** | 补齐后**原有块逐字不变**（`[工作记忆]`/`[语义记忆]`/`[轨迹]` 等按同序同文保留） | `_state` 是「先拼 parts、再按优先级 keep」，评审块在 `[轨迹]` **之前**；加一块只可能挤掉**它后面**的块 |
| **P4** | 补进去的 3 行里，「纯通过语」仍 ≥ 2/3 | 承 V200：同一个账本、同一批条目，只是换了个调用点 |
| **P5** | `_state` 的**调用结构**里，不传签名的不止收尾一处（≥2 处，或 ≥1 处另有他人） | `grep -n "_state("` 只有两处：`core.py:1144`（主循环，传全）与 `core.py:2816`（收尾，不传）。**押「≥2 处」是想错了方向还是对？——押：只有 1 处（收尾），且全库 `run(` 的调用方里 `task_id` 传空的不止 1 个** |

**主判据行（唯一）**：
```
「补签名后收尾 prompt 能净增 3 行评审、且不挤掉任何既有块」= 是 / 否
```

## 2. 装置

```
A 静态（不跑）：全库 `_state(` / `core.run(` / `Core.run(` 的调用点与实参形态（AST）。
               报「哪些调用点不带 task_id」。
B 动态（跑）：6 题 × `prev` 档（账本 = 本机 288 条），每题：
               · 包一层 `Core._state` 记录 (it, task_id, scorer_sha, suite_sha, 输出)
               · 取最后一次**带签名**的 state（= 模型迭代时看到的最后一版）
                 与最后一次**不带签名**的 state（= 收尾那版）
               · 逐块切分（行首 `[块名]`），做差集/并集
C 反事实：用 `_state` **原实现**、把收尾那次的入参换成补齐签名，重算一次；
          比对：字符增量、块增减、`state_trimmed` 增量、原有块是否逐字不变。
```
`state_trimmed` 是 `Core` 的计数器 ⇒ 重算会污染它，装置必须**记前后差值并说明**（不当作产品读数）。

## 3. 会推翻结论的条件（先写）

1. 若反事实 state 的块集合**不是**「原收尾 ∪ 评审」，说明 `_state` 的拼装不是纯函数
   （依赖 `self` 的某些可变状态）⇒ 反事实作废，只报观察值。
2. 若补齐后触发裁剪并挤掉既有块 ⇒ P2 反、P3 反，**这条修法要连带预算一起改**，不能只补签名。
3. 若 `state_trimmed` 在反事实里增了，而增量来自**评审块之外**，说明我归因错了，逐块重算。
