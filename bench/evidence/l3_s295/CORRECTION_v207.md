# V207 更正：failure 分母里有 51.9% 是**离线桩**的产物

> 触发：V208 开工前的免费统计。⛔ 原读数**不删**，只加更正（许撤不许藏）。

## 1. 错在哪

RESULTS_v207 §1 写的是：

> failure 构成：「缺少 def」**584** / 自检或编译 123 / 其它 66 / agent 工具失败 4
> ⇒ 生产库里 **91% 的失败是格式失败**

这两个数**技术上对、解释上错**。原因：`state/memory.db` 里混着**离线桩**跑出来的记录。

桩的两个指纹（`StubLLM` 的固定输出）：

```
finish({'answer': '```c\nint solve0(int x) { return x; }\n```'}) — 第 1 版答案
自检超限未过（3次）— 3/4 项未过：缺少 def solve(...)；代码块语言标签是 'c'（本题要 Python）；编译失败
```

第一条含 `int solve0(int x)`；第二条不含代码原文，但含 `缺少 def solve(` + `语言标签是 'c'` 这对组合
（真模型不会把 Python 题答成 C）。两条都判为桩。

且必须同时说明「其中 74% 是同一次 flatten 失败的重复」。

## 3. 这条更正改了什么判断

1. V207 §2 的「断点① 是缺一个开关」**不变**（生产库 `kind=reward` 仍是 0 条，这是硬事实）。
2. 「库里已有 584 条同一个坑，可拿去做簇级蒸馏」这个想法**作废**：
   584 条里 403 条是桩的，真 215 条里 277 条是同一条重复 ⇒ **原料不是「同一个坑多次」，是「同一次坑的多次拷贝」**。
   纪律 71（一键的实例集是深度的函数）的同型：**重复的 episode 不等于重复的样本**。
3. 因此「造同一个坑多次」这条路**在现有库上不可行**，只能现造（V207 已造 11 条）。
