# PREREG V210：把自评的「元数」那一半拿掉

**写于 2026-11-19 21:10，代码未改、未跑。**（纪律 104：探索轮也先预注册）

## 0. 这一轮只改一件事

V209（§277）判出：同一条 `[外部评审]` 通道，用得好不好取决于**异常信息里哪一半被当成指令**。

| 半 | 例 | V209 实测 |
|---|---|---|
| 异常**名** / 根因 | `TypeError: 'tuple' object does not support item assignment` | t04 idx0 2/20 → **7/20** |
| 异常文的**元数** | `ValueError: not enough values to unpack (expected 2, got 1)` | t01[1..3] 14/15/14 → **2/6/4** |

⇒ 本轮把**元数**那半从投喂里删掉，异常名与失败断言（输入/期望）**原样保留**。

⛔ 不做的事：不改 `why` 的落盘格式、不动打分器、不动 `state` 的块顺序与窗口规则、
不换模型、不改 `cap`/`scope`/`budget`。

## 1. 改动（最小、可逆、默认关）

1. `mw/critique.py` 新增纯函数 `transferable_why(why)`：只认**三类**形态，别的一字不动。
   - `(expected N, got M)` 括号元数（含 `at least`/`at most` 变体）
   - `not enough values to unpack` / `too many values to unpack`
   - 删完剩下的悬空 `:`（`⇒ ValueError:` ⇒ `⇒ ValueError`）
2. `CritiqueLedger(..., why_mode="raw"|"transferable")`，**默认 `raw` = 旧行为一字不改**。
   过滤发生在 `add()` ⇒ 只作用于**被构造出来的那份账本**。
3. `_critique_snapshot(..., why_mode=)`：内核拿到的**快照副本**用 `transferable`；
   真账本（落盘那条）永远 `raw`。⇒ **证据完整，投喂裁剪**。
4. 命令行 `--critique-why {raw,transferable}`，默认 `raw`。⛔ 默认不改 —— 默认值要不要翻，
   由本轮读数决定，不由本轮顺手决定。

## 4. 已知风险与预案

1. ⛔ **过滤器写宽** ⇒ 连 `TypeError` 一起打掉。P1 的第三句就是为它设的正例对照
   （纪律 5：否定断言必须有正例）。
2. ⚠️ **块长会变**：D 的自评行变短，`as_line()[:140]` 会多露出第二条失败断言。
   ⇒ 报告 B/D 每臂的 `[外部评审]` 字符数；⛔ 不得把「长度」当机制（V90：位序成因是词元数，
   但「块长变了」本身不解释方向）。
3. ⚠️ `--critique-why=transferable` 与 `scope=off` 组合无意义（快照不存在）⇒ 在
   `_option_conflict` 里显式拒绝，不静默忽略（同 `--critique-drop` 的先例）。
4. ⛔ 三臂顺序固定 a,b,d；⛔ 不中途改参数；⛔ 不因某一臂读数难看而重跑。
