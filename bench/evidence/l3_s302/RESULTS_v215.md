## 3. 失效模式 A：沙箱 broker 的执行凭据过期（可复核）

第 1 次尝试的 16 次秒级失败，栈**逐字相同**：

```
mw/critique.py:224  save
  → sitecustomize.py:884  _brokered_path_mkdir
    → sitecustomize.py:604  _broker_request_host_operation
      → sitecustomize.py:500  _broker_send_request
_BrokerProtocolError: execution attempt 不存在或已关闭
```

- 内核**没有崩在内核代码上**：栈全在 WorkBuddy 沙箱 shim。
- 同一个 `order.txt` 里，前 23 次 `rc=0`、后 17 次 `rc=1`，**边界干净**（19:48:47 一秒内翻面）。
- 崩后实测 ollama **存活**（`/api/tags` 返回 4 个模型，含 `qwen2.5:7b`）⇒ 不是模型端。

**机制**：`PYTHONPATH` 指向 shim，所有 `open/mkdir/cp` 都走 unix socket +
`CODEBUDDY_SANDBOX_BROKER_EXECUTION_ATTEMPT_ID`。一次工具调用一个 attempt；
长跑的后台 shell 一旦错过它，**后续每一个文件操作都秒失败**。

**修法（已落地 `run_b.sh`）**：整段脚本 `unset PYTHONPATH` + 绝对路径调 `python3`/`cp`/`mkdir`，
跑前正例自校验 `'sitecustomize' in sys.modules == False`（实测 `SHIM_LOADED False`）。

## 7. 自踩 4 条

① ⛔⛔ **`alarm` 在后台派生的进程里不生效，在前台生效** —— 同一个 `perl -e 'alarm shift; exec @ARGV' 420`：
   前台 `python3 -c "sleep 20"` 用 `alarm 3` **3.0 s 被杀**（rc=142）；
   后台批量里同一条命令，运行 **41 分钟**（21:32→22:13）、**49 分钟**（22:58→23:47）都没被杀。
   ⇒ 两种启动路径行为不同，与纪律 88（"变体没接上"）同型。**成因未证实**（候选：
   SIG_IGN 被继承 / 后台 shell 的进程组），但**修法不依赖成因**：改用后台 `sleep` + `kill -9 $pid` 看门狗。
② ⛔ **"能连上"冒充"能干活"**：`curl /api/tags` 0.28 s 正常、`/api/chat` 8 token 0.28 s 正常，
   而真实规模调用 2.7 tok/s ⇒ 差 **50 倍**。速度必须用**接近真实的负载**量，不许用小探针。
③ ⛔ **改完装置不先量就开批量**：修好 broker（F1）后直接启动 20 次，49 分钟 0 产出。
   正确顺序是 **量速度 → 过门槛 → 再启动**（G1）。
④ ⚠️ **一次运行都没完成时，`order.txt` 是空的**：`rc` 只写"跑完的运行"，
   所以"0 行"和"装置没启动"在读号上同形 ⇒ 必须同时看 `runs.jsonl` 行数 + 日志首个时间戳。
