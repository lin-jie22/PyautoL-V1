## §2 机制

```
propose(观测, 套件id, done=MET过的gid) -> [Goal]     # 纯函数
evaluate(goal, 观测) -> (MET|NOT_MET, reading)      # 只有两个值
record(账本, goal, verdict, reading)                # 追加，不覆盖
```

| 类 | 触发（全部来自账本） | 判据 | 能自己闭环 |
|---|---|---|---|
| `COVER` | 题在套件里，账本 0 行 | `n_obs ≥ 1` | ✅ |
| `PROBE` | `0 < n_obs < 3` | `n_obs ≥ 3` | ✅ |
| `RAISE` | `mean_score < 1.0` | `mean_score ≥ 1.0` | ⛔ 不能 |

排序＝词典序（COVER > PROBE > RAISE，同类按缺口升序）。⛔ 不做收益/成本加权 ——
那是一个需要被单独验证的预测模型，拿它决定先做哪件事再拿结果当它的证据是循环论证。

观测写 `state/goal_obs.jsonl`，⛔ 不写 `score_ledger.jsonl`（后者带 `caliber_sig` 闸，
混进不同口径的观测等于伪造履历 —— 自我模型会据此高估自己）。

## §3 P4 为什么 FAIL（不解释掉）

今天 40 格里 **34 格零覆盖**，而「零覆盖」的定义就是**没有任何读数**。
34 条目标在所有判据维度上完全并列 ⇒ 「先做哪一条」只能靠 id 字典序 ⇒
**那是一段人写的常量**。

四种扰动都改不动它：
- `drop_last_session`（改 36 行）：动的是有观测的格子，不是零覆盖那 34 格；
- `boost_one`（改 **0** 行）：该格原本已是 1.0 ⇒ **扰动哑火**（纪律 88）；
- `drop_cell`（改 6 行）：目标集变了（Δ=2），但 top-1 仍是 id 最小的那条 `COVER`；
- `append_round`（改 11 行）：全格 +1 次观测，仍在 `PROBE`，排序不变。

⭐ 唯一能让这条判据变绿的办法是给排序加一个与数据无关的种子 ——
那是把判据刷绿，不是把系统做对。**如实记 FAIL。**

⭐ 但目标**内容**是读数的函数：逐目标「改掉它引用的读数 ⇒ 该目标消失/换类」= **40/40**。
所以 FAIL 的准确含义是：**「做什么」是读数决定的，「先做哪一条」在并列时不是。**
