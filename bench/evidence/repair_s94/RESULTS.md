## 5. 新缺陷（不在预注册里）：交付物是工具调用轨迹

`answers_v2_7b.jsonl` 30 行里有 **6 行**（`sg01`×3、`sg10`×3）的答案是：

```
[step 1] finish({'answer': "```python\ndef norm_sg01(rows):\n    # ① 去掉每行首尾的空白字符\n ...
```

不是代码，是**模型把上一轮看见的轨迹格式照抄了一份当答案**，而内核把它原样收下、原样交付。
内核自己的收尾闸当场喊了：

```
🧪 收尾交付**未过闸**：2/5 项未过：缺少 def norm_sg01(...)；编译失败 line 1: invalid character '—' (U+2014)
```

但仍然交付（`closed ... ⚠️本次交付未过自检 | 收尾闸=1跑/0过/1未过`）—— 这是 §57 的设计
（置标不拦），设计没问题；问题在**上游**：这条路没有任何机制让模型重新给出代码。

⇒ v2 的 84 格「无闸」池、以及本轮 +29 里的 28 格，都由这一条造成。
⇒ 这与 §50/§86 的 K1/K2 同宗：**交付通道的病，不是能力的病**。

附带核实一条已知欠账：`answers.jsonl` 的 `rep` 字段 **30 行全是 1**（题序是 rep-major，
所以靠行序仍能还原轮次；`audit_loss_pool.py` 的 V3 反证就是查这个）。

## 7. 边界（⛔ 越界即作废）

1. **不是跨题族**：v2 与 v3 是同一形态（「按 N 条编号规则实现一个函数」）的两个实例集。
   本轮能说的最强话是「不依赖 v3 那 10 个具体实例」，**不能**说「不限于这一族」。
2. **首答是内核产的，第二请求的 system 是 `DIRECT_SYSTEM`** —— 两者不是同一个提示词。
   两臂完全相同 ⇒ 不影响 `R−P`；但绝对分不许与任何 `direct` 口径并列。
3. `repeat=2` 的「噪声 0」只说明**本轮内**四格相同，**不是**跨进程噪声下限
   （那个得按 `noise_floor.py` 的 MIN_RUNS=5 另测）。
4. 本轮 v2 首答用 **rep1** 当起点；`sg02`/`sg05` 三轮不稳定（7/10/10、0/1/0）
   ⇒ 若改用 rep2 的三份首答，`sg02` 的旧分是 **10** 而不是 7，起点就换了。
   **「+29」这个数字对起点轮次敏感，「R−P = 0」不敏感**（两臂同步移动，
   且 16/20 逐字节相同这件事与起点无关）。
   ⛔ 本轮的 `+29` 不能当成一个稳定常数引用。
