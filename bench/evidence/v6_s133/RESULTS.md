# V43 判决：产品验收第一格 —— 修一处接线，真实任务从「没有产物」变成「产物正确」

证据目录：`bench/evidence/v6_s133/`（`PREREG.md` / `logs_a_failover0.log` / `logs_b_failover1.log` /
`p5_afterfix.txt` / `sales.csv`）。代码：`run.py`（`_build` 的 guard 构造位置）+ `tests/contract_test.py`（AZ106）
+ `bench/withdraw_check.py`（AZ106 撤回态）。

## 一、判决（三句话，必须分开说）

> **① 修之前，这个内核接到一个不属于 bench 题面的任务时，产出是 0 —— 一个文件都没写出来。**
> **② 病因不是「模型笨」，是 `--allow-shell` 只在离线分支上通电**（`run.py:158-171`），
>    真模型路径永远 `allow_shell=False` ⇒ 唯一能干活的动作被 guard 拦掉。
> **③ 修了这一处接线后，同一个任务、同一个模型、同一组旋钮：`run_shell ok=True`，
>    `report.md` 写出来了，三个区域的合计全对。**

⛔ 但仍然**不能说「能成产品」**：单例、7B 模型、格式不合要求、状态是 `stalled`。见 §五。

## 二、三臂对照（同一个任务、同一份数据、同一个模型）

任务（冻结于 `PREREG.md §1`）：工作目录的 `sales.csv`（5 行）→ 按区域汇总 → markdown 表格 → `report.md`。
正确答案：华北 2700 / 华南 2000 / 华东 700。

| 臂 | 时刻 | `cand_failover` | shell 通路 | 墙钟 | 状态 | `report.md` | 数字 |
|---|---|---|---|---|---|---|---|
| **A** | 12:56 | 0（默认） | — | 74s | `stalled` | **不存在** | — |
| **B** | 12:58 | 1 | **被 guard 拦** | 79s | `done` | **不存在** | — |
| **C** | 13:13 | 1 + 接线修复 | **`ok=True`** | 71s | `stalled` | **存在 44 字节** | **全对** |

A 与 B 之间只差 `cand_failover`；B 与 C 之间只差这一处接线。
⇒ 三臂不是三个实验，是**同一条因果链上的三个点**。

## 三、B 臂的病历（`logs_b_failover1.log`，原文）

```
12:58:53  ↪ 交付被打回 ⇒ 让位给候选 2/5（不重规划，直接用已有的）
12:58:53  ✋ [guard:tool_misuse] 拦截 —— shell 未开启（需显式 --allow-shell）
12:58:53  ⛔ 全部候选被拦 (2 次连续失败)
12:59:09  ⏭ 重复动作已跳过（不产生新信息）: run_shell
```

**命令行确实带着 `--allow-shell`。** 原因在 `run.py`：

```python
if args.offline or not s.llm.usable():
    ...
    core.guard = Guard(allow_shell=allow_shell, ...)   # ← 只有这一支
else:
    core = Core(...)                                    # ← 真模型走这里，不传 guard
```

`Core.__init__` 是 `self.guard = guard or Guard(...)` ⇒ 默认 `allow_shell=False`。

**这是「机制存在 ≠ 机制通电」的第五种形态：开关只在一条没人走的分支上通电。**
前四种（§87/§99/§107）是「开关没开 / 载荷送不到 / 检测器自己失效 / 输出接在记录仪上」。
这一种更阴：那条分支**恰好是离线桩**，而**门禁每跑一次都在走它** ——
所以 605 条契约没有一条能发现，只有真模型路径是坏的。

## 四、修复（唯一改动）

把 `Guard(...)` 从 `if` 里提到**两条分支之前**，作为 `guard=` 参数传进 `Core`
（⛔ 不用「构造后 `core.guard = …` 覆盖」：那会让「谁拿着哪个 guard」取决于构造顺序，
正是本轮在修的病）。契约 **AZ106** 四格钉死：

| 格 | 期望 | 修之前 |
|---|---|---|
| 联网 + `allow_shell=True` | True | **False ⇒ 红** |
| 联网 + `allow_shell=False` | False | False（对） |
| 离线 + `allow_shell=True` | True | True（对） |
| 离线 + `allow_shell=False` | False | False（对） |

⛔ 四格的理由：**只测离线那一支永远绿** —— 门禁平时走的就是它。只测一格等于没测。

撤回态（`bench/withdraw_check.py` AZ106）：把联网分支退回「不传 guard」
⇒ `红=['AZ106']`、多红=无、还原后基线 `606/0`。

## 六、C 臂暴露出的四条**没修**的病（V44 的题目）

⛔ 本轮一律不修：它们和「接线」不是一个层级，混在一起修会让「修完之后有没有变好」不可归因。

| # | 事实 | 证据 |
|---|---|---|
| D2 | 第 1 轮 5 个候选里，有 **3 个是同一个 `agent:code_agent`** ⇒ 「候选数 5」≠「互不相同的 5」 | B/C 臂各 3 行 `重复动作已跳过` |
| D3 | 外部能力 `code_agent` 的适用前提是硬编码「题面里必须有『函数名必须是 X』」⇒ 真实任务上**必然**不适用，但它占了 1/5 的宽度 | 两臂同一句 `RuntimeError` |
| D4 | 一次被 guard 拦掉的动作会进「已试过」集合 ⇒ **下一轮同一个动作被当重复跳过**（B 臂 12:59:09）。C 臂里 `run_shell` 成功之后也会同样被锁死 | 两臂日志 |
| D5 | C 臂状态是 `stalled`，而产物正确 ⇒ **状态词不检查约定产物**；B 臂状态是 `done`，而产物不存在 ⇒ **`done` 会撒谎，`stalled` 也会** | 两臂状态行 + `ls` |

D5 是产品最致命的一条：**用户唯一能看的信号（状态）在两个方向上都不可信。**

## 七、这一轮对主线意味着什么

MEMORY §零 要求每轮回答「有没有让累积循环离可测更近一步」。老实回答：

**这一轮不是内核变强，是把「产品能不能」这个问题第一次变成了可读的数。**
它服务主线的路径是**间接但硬**的：

- V41/V42 的死结是「让位没弹药」（机会窗口 8/64）。为什么没弹药？
  因为题目一步就做完（40 题全是「写一个函数」），规划器给不出第二个候选。
- 本轮证明：**真实任务上第 1 轮就有 5 个候选** —— 弹药不是不存在，是**只在 bench 题面上不存在**。
- ⇒ 想量「让位有没有用」，**必须先在会让让位有机会的题面上下注**。这一格现在有了。

⛔ 仍不许说「系统会自己变强」：本轮没有一条累积读数，一个格都没动。

## 八、对「现在能不能成产品」的答案

**不能。但距离不是「两个量级」，是三条具体的、可逐条关掉的错配：**

| 错配 | 现状 | 关掉它要做什么 |
|---|---|---|
| **提示词错配** | 规划器按「解题」写（`DIRECT_SYSTEM`，`run.py:144`），真实任务上只会想到「调个 agent」 | 单开一段（会断所有历史 `caliber_sig`），写「干活」形态 |
| **外部能力错配** | `code_agent` 只认「函数名必须是 X」 | 按任务类型分派，或废掉它 |
| **测量错配** | 40 题全是单函数，测不出「能不能干活」 | 产品验收用例（单例、手工判、不入台账）——本轮已建第一个 |

⇒ 而「工具面太少」**不是**错配：`run_shell` + shell 白名单已经够干这类活，缺的是**提示词不让它想到**。
