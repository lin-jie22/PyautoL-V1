## 1. 要回答的问题

V60 判完两件事，剩下的那句话是**没被检验**的：

> 放开 shell 后模型 **4/4 全跑了**，但 **验证只落在已经做对的题上**
> （`top_k`/`rle` 各跑 2 次；`merge_ranges`(0.3333) 22 轮里一次没提）
> ⇒ 病位不是「权限」、不是「顺序」，是**验证根本没落到错的题上**。

这句话有两个可测成分，本轮分开量：

| 记号 | 问题 | 需要什么 |
|---|---|---|
| **Q1 触发** | 把验证放进**交付闸**（不再由模型选）后，它**会不会真的跑**、跑在哪些题上？ | 新读数 `kernel_verify` |
| **Q2 兑现** | 它**抓不抓得到**真错（`merge_ranges` 的 `TypeError`），抓到后**分数变不变**？ | 两臂 `mean` + 逐题 `score` |

⚠️ **Q1 是必须动内核的唯一理由**：现有账本没有一格记录「交付闸跑过几次、哪一类判据拒的」。
`verify_stats` 只活在进程里（`run.py` 里 0 处引用），`kernel_*` 里也没有 `verify`。

## 2. 装置可达性（押注前先确认载荷能到押注的格子 —— 纪律 6）

### 2.1 判据的**输入**从哪来：题面自带的示例，**不是** `tests`

V60 那轮的教训是「`rc=0` ≠ 对」。要让验证产出**可比对的结果**，就必须有期望值。
本项目**不许**把尺子（`tests`）喂给自己，所以期望值只能来自**题面**：

| 题 | 题面里的示例（`prompt` 字段原文） | 抽出条数 |
|---|---|---|
| t01 parse_duration | 只有输入 `'1h30m'、'45s'、'2h'、'10m'`，**没有 `==`** | **0** |
| t02 dedupe | 无 | **0** |
| t03 commas | `commas(1234567) == '1,234,567'`、`commas(0) == '0'`、`commas(999) == '999'` | 3 |
| t04 merge_ranges | `merge_ranges([(1,3),(2,6),(8,10)]) == [(1,6),(8,10)]` | 1 |
| t05 top_k | `top_k(['a','b','a'], 1) == [('a', 2)]` | 1 |
| t06 rle | `rle('aaabbc') == '3a2b1c'`、`rle('') == ''` | 2 |

⇒ **4/6 题有示例、共 7 条断言**（静态抽取已用一次性脚本验过，抽取器写进 `mw/verify.py`）。
⚠️ t01 是**唯一一个"分数不满且题面没示例"**的题（0.8333）⇒ 它**结构上**不可能被这条判据救，
这不是装置失效，是判据的来源边界。**P7 专门押这一条**。

### 2.2 真错会不会被这条判据接住

V60 的 `per_task[].why`（**上一轮的产物**）写着 t04 两 rep 同一条：

```
失败: assert merge_ranges([(1,3),(2,6),(8,10)]) == [(1,6),(8,10)]
      ⇒ TypeError: 'tuple' object does not support item assignment
```

⇒ 是**运行期**错误：`compiles` 过、`undefined` 过（没有未定义名）、`defines` 过。
**静态判据结构上抓不到它，只有执行能抓到**。这正是 V80 那句「不做执行」判词**该被重开**的
具体理由 —— 那时反对的是「派生的探针输入」（一处新判据来源），而现在输入是**题面自带的**。

### 2.3 结论

| 检查 | 结论 |
|---|---|
| 七条断言能否在"答案代码 + assert"上一次执行完毕 | ✅ 纯表达式、无 I/O、无网络 |
| 会不会挂死 | 有界：`subprocess.run(timeout=5)` + `python3 -I -B` + 独立 tempdir |
| 会不会被 workspace 残留污染 | ⛔ 不进 `ws/`：`tempfile.mkdtemp()` 里跑，`-I` 关掉 `sys.path` 的 cwd 项 |

## 3. 两臂（单变量：只差 `V1_VERIFY_EXEC`）+ 一个**常量**

| 臂 | 命令差异 | 其余**逐项相同** |
|---|---|---|
| **A**（对照） | `V1_VERIFY_EXEC=0`（= V60 的内核行为） | 模型 `qwen2.5:7b` / T=0 / `max_tokens=1024` / `max_steps=12` / `state_chars=2400` / `max_candidates=3` / `verify_retries=2` / `verify_static=2` / `repeat=2` / `--no-external --no-ledger --no-answers` / **两臂都带 `--allow-shell`** |
| **B**（实验） | `V1_VERIFY_EXEC=1` | 同上 |

⭐ **为什么 `--allow-shell` 是常量而不是变量**：V60 已经把它判完（4/4 采用、Δ 分=0）。
本轮要量的是"**内核**强制跑"，模型那侧的 shell 必须**两臂都在**，否则第二个变量就是它。
⚠️ 代价：A 臂不再与 V60 的 A 臂（shell 关）逐字节相同 ⇒ 与 V60 的比较只能是**分数层面**的。

⭐ **两臂 `caliber_sig` 这次应当不同**：`verify_exec` 进 `Limits` ⇒ 进 `as_dict()`。
这与 V60 相反（那时 `allow_shell` 在 `Guard` 上、不进口径），本轮可顺手证明
「开关进了口径 ⇒ 签名真的会分开」：**P9 押 A 臂 sig ≠ `542f9053d19a7090`**。

⛔ 两臂共用同一个 workspace 路径，每臂开跑前清空（路径若进提示词，两个路径 = 偷偷加变量）。
⛔ 不接管道（SIGPIPE ⇒ 137），只重定向；`python3 -u`。

## 4. 新增读数（两个出口，都**只当量具**，不当实验变量）

### 4.1 `kernel_verify`（新账本键，8 键 + 1 派生）

分母**三个，不许合成一个**：

| 键 | 分母 | 答什么 |
|---|---|---|
| `tasks` | 题 | 一共几题进了闸 |
| `runs` / `passed` / `failed` | 次（闸被调用） | 闸跑了几次、拒了几次 |
| `exhausted` | 次 | 打回超上限、如实交付的（**代价面**） |
| `example_tasks` | 题 | 题面里抽到了示例的题数（= 判据的**适用面**） |
| `example_runs` / `example_failed` | 次 | 示例判据真执行了几次、拒了几次 |
| `exec_err` | 次 | **装置自曝**：超时 / 子进程异常 / 无解释器 |

⛔ 派生量 `verify_gap = runs − (passed + failed)` 只在落盘行出现、**不进零点**
（V58/V60 已踩两次）。

### 4.2 `kernel_shell.trace_cmd`（14 → 15 键）

V60 自踩第一条：`trace` 只写 `r2:1`，**命令原文不在账本里** ⇒ 4 条命令不可审计。
本轮把 `sha8 + 单行命令前 60 字` 搬进账本。⚠️ 它**必须有分母** ⇒ 两臂都开 shell（§3），
预计 `dispatched=4`（V60 B 臂实测），不再是"加了量具但没有读数"。

**押错时怎么读（先写好，不许事后解释）**：

- P3 落空且 `example_runs=0` ⇒ 判据**没通电**（`derive` 没被调用 / `_check_one` 没走新分支）⇒ 本轮**作废，不算负结果**。
- P3 落空但 `example_runs>0` 且 `example_failed=0` ⇒ t04 的 `TypeError` **在我这条判据下不复现**（例如交付的代码与 V60 不同）⇒ 真负结果，要查 `ws/` 残留比对。
- P5 落空（平）⇒ 「强制验证」把**动作**放出来了，**没把修正放出来** —— 与 V60「放开 shell」同构，修法要换成"给模型看 `assert` 的**实际输出**，不只是异常名"。
