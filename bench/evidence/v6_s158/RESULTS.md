### 1.1 计划序列（每臂 3 跑完全相同，取 r1）

| 题 | `e0` 无块 | `e1` 真载荷 | `e2` 等长安慰剂 |
|---|---|---|---|
| `g7d2_dedupe_keep` | `[1]c1k1:finish` | `[1]c1k1:finish` | `[1]c1k1:finish` |
| `g7d3_fmt_amount` | `[1]c3k3:recall` ‖ `[2]c1k1:finish` | **`[1]c3k3:finish`** | `[1]c2k2:finish` |
| `g7e1_parse_flag` | `[1]c3k3:finish` | **`[1]c3k2:finish`** | **`[1]c1k1:run_shell` ‖ `[2]c1k1:recall` ‖ `[3]c1k1:finish`** |
| `g7e2_truncate_tail` | `[1]c3k3:finish` | `[1]c3k3:finish` | **`[1]c1k1:recall` ‖ `[2]c2k2:finish`** |

⭐ **`e1` 与 `e2` 只差语义、同长 84 字符，却给出两种形状**：
**真载荷 ⇒ 一次给 3 个候选、一步交付（`cands_total=10`、4 轮）；等长安慰剂 ⇒ 每轮 1 个候选、逐步探索（`cands_total=9`、7 轮、`run_shell` 查文件再 `recall` 查惯例）。**
⇒ 起作用的是**内容**，不是「块在场」、不是长度、不是 token 数（长度与行数逐题相同）。
⚠️ 这与 V23（`v6_s114`）在**分数**层量到的形状**相反**（那次 `e1ni` 上 A1≡A2 逐字节相同）——
两轮测的不是同一层，⛔ 不相减、不互相废止。

⚠️ **`rewards_seen` 三臂不同（`e0=72` / `e1=60` / `e2=102`），⛔ 不许读成「e2 读得更多」**：
它是**逐次 `guidance()` 求和**的读取量（`worldmodel.py:656`），而三臂的**轮数**不同
（`e0=5` / `e1=4` / `e2=7`）⇒ 这个数随计划长度变化，**是计划的结果，不是计划的输入**。
臂内 3 跑该数逐字相同（72/60/102）——这一条才是本轮的证据。

### 1.2 ⚠️ 押错在哪：方向不是「更多检查」

载荷原文是「`AssertionError` 出现过 12 次（均值 0.40）⇒ **先检查**：用题目给出的示例输入，把当前实现手算一遍」。
模型的实际反应是 **减少**检查：`e1` 上 `g7d3` 的 `recall` 被抹掉、`g7e1` 的候选种类从 3 降到 2；
而**没有任何含义的填充**反而把模型推向 `run_shell` + `recall`。

⭐ 最合理的读法（未单独验证，⛔ 不当结论）：**「被告知会错在哪」被当成「已经知道错在哪」** ⇒ 省掉自查。
这与 V62「看到反例不改」同族，但位置又换了一层：**这次连"去看"都省了。**

## 2. 最硬的一条：三臂交付同一份错代码，同分

`g7e1_parse_flag` 三臂的交付都以同一段开头：

```python
def parse_flag(s):
    s = s.strip().lower()
    if s in ('true', '1', 'on'):
        return True
```

`e0` 意图写「根据项目惯例直接写代码」、`e1` 写「直接实现函数逻辑」、`e2` 走完三步探索，
**产物与分数（0.20）逐格相同**。
⇒ 计划层可测的差异，在分数层是 **0**。这是本项目至今最干净的一次「**计划 ≠ 瓶颈**」取证。

## 3. 病根：`recall` 查惯例，库里没有

`e2` 的 `parse_flag` 第三步 `state_dump` 原文（`e2/r3/state_dump.jsonl`，`it=3`）：

```
[工作记忆] [75字 sha=9ce15f106877] run_shell ⇒ ✔ rc=1
[stderr] cat: parse_utils.py: No such file or directory ｜ [23字 sha=34ea10ccd32e] recall ⇒ ✔ (语义记忆中无相关条目)
[轨迹] [step 1] run_shell({'cmd': 'cat parse_utils.py'}) — 检查已有代码实现 ⇒ 成功
       ｜ [step 2] recall({'query': '开关解析惯例'}) — 确认解析规则 ⇒ 成功
```

⭐ **`recall` 去查「开关解析惯例」，返回「语义记忆中无相关条目」。**

库内实况（`seed_memory.db`）：

| 项 | 数值 |
|---|---|
| `facts`（语义记忆） | **1** 条（与本题族无关） |
| `episodes.kind="reward"` | 24 条，**`passed: true` 的 0 条** |
| `episodes.kind="finish"`（交付原文） | 24 条，**全是错交付**（例：`fmt_amount` = `f"{x:,.2f}"`，而断言要 `'1 234.50'`） |

⇒ **这 4 题在历史上从未成功过**（`g7d3` 136 次、`g7e1` 135 次从未 1.0），
所以累积库里**没有任何"对"可复用**：只有错的交付 + 失败计数。
计划改多少次、探索多少步，都只能撞回同一个默认写法。

## 4. ⭐ 下一刀的位置（由 §3 直接推出，本轮未动）

失败原文里**本来就有真值**，是载荷把它丢掉的：

```
meta.failure = "通过 1/5；失败: assert parse_flag('y') is True ⇒ AssertionError
                | assert parse_flag('true') is False ⇒ AssertionError | …"
```

`reward_guidance` 只把这段压成 `_error_class(...)` = `AssertionError` + 次数 + 均值
（`mw/worldmodel.py:650`），**`== 期望` 那一半被丢掉**。
⇒ 载荷现在说的是「你这类题常错」，而不是「这几个输入应该得到这几个值」。

⚠️ 边界：V62 判过「位置不是病，模型不看反例才是」，那次的"反例"是**执行 traceback**；
这次的"反例"是**`输入 → 期望` 对**，形状不同 ⇒ 不算重开，但**必须先量这 4 题的历史失败里
`assert … == …` 的真值覆盖率**再决定，⛔ 不许直接改载荷就押分数。
