# V113 预注册（**跑之前落盘**，第 191 轮）

> 目录：`bench/evidence/v6_s202/`
> **零模型、零网络、零子进程**：输入全部来自 V111 的 `behaviour.json`（26 实现 × 5 条 test 的实际输出）。

## 0. 为什么问这个

V104~V112 九轮把「尺子」量透了，但一直在**加法的反面**：什么不管用。
V113 换问法：**系统能不能从「这次错在哪」直接读出「该改什么」？**

V110 的删除式干预有一个已经量出的局限：**它只能解释已经存在的代码**（删掉某惯用法看分数掉不掉），
**找不到「缺失的东西」**。而 `075b4099`（0.4）缺的正是「一个它根本没有的替换」。

⭐ 从 `test 失败` 反推，是唯一不依赖「已有代码里有什么」的通道。

## 1. 装置

对每一个「实际输出 ≠ 期望值」的格子，用 `difflib.SequenceMatcher` 求**最小编辑脚本**，然后分类：

| 类型 | 定义 | 对应的修复动作 |
|---|---|---|
| **A** `single_sub` | 恰好 1 个 `replace`，两条长度都是 1 | `X.replace(a, b)` 一个动作 |
| **B** `edge` | 只有首/尾的 `insert`/`delete` | `prefix + X` / `X + suffix` |
| **C** `multi` | 多个替换 / 中间插入 / 长度差大 | 需要结构改动 |
| **D** `error` | 输出是 `ERROR:<类型>` | 编译/运行期故障，不是输出错 |

⛔ **A 类的「修复动作」是构造性的**：`replace(a,b)` 一定能把这一格修好（在只看这一格的前提下）。
⇒ A 类比例高**不代表能修好整个函数**（多条 test 可能要求互相冲突的动作）。这一点必须单独量。

## 2. 判据（三值，跑前写死）

| 编号 | 命题 | 押 | 判负后果 |
|---|---|---|---|
| **Z1** | **A 类（单字符替换）占全部失败格的比例 ≥ 50%** | **否（< 50%）** | 若 ≥50% ⇒ 「失败大多是一个字符的事」，V106 的「无梯度」与这个矛盾，须重新解释为什么盲搜找不到 |
| **Z2** | **至少有一个非满分实现，能被「对它全部失败格求交集的动作」一次抬到 1.0** | **有** | 若 0 个 ⇒ 「从 diff 反推」只对单格有效、对函数无效，这条通道关闭 |
| **Z3** | **A 类动作在跨 test 上不冲突**（同一实现的多个失败格给出同一动作） | **成立** | 若冲突 ⇒ 「逐格反推」必然要仲裁，而仲裁需要语义，不是 diff 能给的 |

## 3. 分母口径

- Z1 分母 = **全部失败格**（26 实现 × 5 test − 通过格）。写进输出行。
- Z2 分母 = **非满分实现数**（26 − 满分实现数）。
- Z3 分母 = **有 ≥2 个失败格的实现数**。
- ⛔ 每题分开报，不合并。

## 4. 已知陷阱

1. **A 类动作「能修好这一格」是构造性的**（`replace(实际, 期望)` 当然能修好）。
   ⇒ 真正的问题不是「能不能表达」，而是**多条 test 的动作是否一致**（Z3）。
2. 输出里含引号（`repr` 的产物）⇒ 比较前必须 `ast.literal_eval` 还原成真值再转 str。
3. 用例外的 `$`、`_` 填充等属 C 类，**不算失败类型学之外**。
4. 语料仍是 4 题 / 26 实现 ⇒ 只说「在这 26 个里」。
5. ⛔ 不许把「A 类覆盖率高」读成「系统会修 bug」：本轮只量**表达能力**，不量**搜索能力**。

## 5. 输出

`READINGS.txt`：§0 失败格总表（逐格：实际/期望/编辑脚本/类型）→ §1 类型分布 → §2 Z1/Z2/Z3 → §3 逐实现的动作交集。
