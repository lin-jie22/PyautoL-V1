## §0 要回答的问题

V116 的结论是：**0.8 处同分不同盆，贪心只看分数所以选了死盆**；搜索真正修好 **1/13**。
它同时也是个负结果：**给了 test 源码（ON 臂）一个候选都没多走**，于是 V115 的「信息层级」被判为「施加下的效应」。

V117 只改一个变量：**同分候选保不保留**（beam 宽度 `k`）。要判的是：

1. **「tie-break 是唯一卡点」这句话是不是因果的**（若 `k=2` 就能到 8/8，则是；若不能，则须判破）。
2. ⭐ **ON/OFF 那个「零效应」是不是被策略掩盖的**。V116 说「搜索策略能把信息层级效应整个吃掉」——
   如果加大 `k` 后开关效应重新出现，那句话就从「相关」升级为「**可复现的掩盖**」，并且能被同一装置解除。

## §1 装置与唯一变量

候选生成器、模板集（T1 常量替换 / T2 容器插入 / T3 返回值包装 / T4 比较主语包装）、判据（`bench/scorers/code_exec.py`）
**全部沿用 V116，一字不改**。唯一变量 = **beam 宽度 `k`**。

| 臂 | `k` | 含义 |
|---|---|---|
| k=1 | 1 | **等价于 V116 的贪心**（本轮当作忠实性对照，必须逐字节复现） |
| k=2 | 2 | 每轮保留**分数最高的前 2 个**（同分按生成顺序） |
| k=3 | 3 | 同上，前 3 个 |

六条臂 = `k ∈ {1,2,3}` × `信息 ∈ {OFF, ON}`。OFF/ON 的词表定义**沿用 V116 §0**（ON = OFF ∪ test 源码 token）。

### §1.1 beam 的精确定义（先把规则写死，否则「唯一变量」不成立）

```
frontier = [(baseline_code, s0)]        # 单起点
visited  = {baseline_code}
for round in 1..6:
    pool = []
    for node in frontier:               # 按 frontier 顺序
        for (lab, src) in candidates(node.code, S):   # 按生成顺序（与 V116 同一顺序）
            if src in visited: continue
            s = score(src)              # 内联复算，见 §1.3
            if s > node.score:          # ★ 只收**严格改进**的孩子（与贪心的判据一致）
                pool.append((s, lab, src, node))
    if pool empty: → exhausted, 停
    visited |= {src for ... in pool}
    frontier = pool 按 (score 降序, 入池顺序升序) 取前 k 个
    if 任一节点 s >= 1.0: → 停，记 s1 = 1.0
s1 = max(node.score for node in frontier)（若中途未到 1.0）
```

- ⭐ 用「严格改进」而不是「不低于当前」是刻意的：**`k=1` 才能与 V116 的贪心逐字节等价**（贪心要求 `s > best_s`）。
- `visited` 是新增的防护（贪心不需要，beam 可能来回编辑成环）。**它不是变量**：`k=1` 时它不改变任何一条路径（贪心单调升分，不可能回到访问过的更差节点）。

### §1.2 判分口径

`score = 通过 test 的条数 / test 总数`，由 `bitmap()` 内联执行得到。
**前置已验证**（`probe.txt` §0）：V116 用**子进程判分器**给这 743 个候选打的分，与本轮内联复算
**错位 0**。⇒ 内联复算不是新尺子，是同一条判据的免子进程实现（beam 会把判分数放大 k 倍，不内联跑不完）。

### §1.3 跑前取证（已做，`probe.py` / `probe.txt`）

`g7e1` 的 4 个卡住实现，**第 1 轮同分集合恰好 2 个**，生成顺序上第 0、1 位分别是：

| 位次 | 动作 | 行为位图 | 盆 |
|---|---|---|---|
| #1 | `T1:ret:=False` | `[T,T,T,T,F]` 掉 t4 `'maybe'` | **死盆**（V116 §5.1：0/4 可达 1.0） |
| #2 | `T2:cont:+'true'` | `[T,T,T,F,T]` 掉 t3 `'on'` | **活盆**（4/4 可达 1.0） |

⇒ **`k=2` 恰好把两个盆都留下**。同时 `g7d2` 两个卡点（`480ada8e` 0.4、`74aa48d8` 0.8）的同分集合**都只有 1 个** ⇒ 无并列可留。

⚠️ 取证只用来看「同分集合多大」，**不预判终点分数**；终点由 `beam.py` 实跑。

## §2 押注（只押结构性命题；分母写进字段名）

| # | 押注 | 依据 |
|---|---|---|
| **W1** | `k=1` 两臂 × 13 实现（`n_impl_g7e1=8`、`n_impl_g7d2=5`）的 `s1` **逐项等于 V116 `search.json`**，且 `exhausted` 状态一致 | 忠实性：`k=1` 就是贪心 |
| **W2** | `ON × k=2` 在 `g7e1` 上 **8/8** 到 1.0（V116 是 **4/8**） | 第 1 轮同分集合 = {死盆#0, 活盆#1}，`k=2` 两个都留；活盆 `+'on'` 可达 1.0 |
| **W3** | `OFF × k=2` 在 `g7e1` 上**仍是 4/8** | 活盆留住了，但 `'on'` 只在 test 源码里 ⇒ OFF 词表到不了 1.0 |
| **W4** | `g7d2` 上 **6 条臂全部逐字节相同** `[1.0, 0.4, 1.0, 0.8, 1.0]` | 该题两个卡点同分集合都只有 1 个 ⇒ 开关与宽度都无对象 |
| **W5** | `ON × k=3` 与 `ON × k=2` 在 `g7e1` 上**逐字节相同** | 同分集合只有 2 个，第三个名额空着 |
| **W6** | 新修好的实现**恰好是** V116 卡在 0.8 的那 4 个（`1aa5099d`/`37a4f17f`/`a579b07a`/`f2d1efa6`），且**只在 ON 臂** | 押「集合身份」不押比率 |

⭐ **W2+W3 合起来是本轮的主结论**：`k=1` 时开关效应 = **0**（V116），`k=2` 时 = **4 个实现**。
⇒ **「给了信息却没用上」不是信息的问题，是策略的问题；而策略的修正量恰好等于「同分集合的大小」。**

## §3 可证明项（不押，直接写公式）

对任意实现、任意轮次，`frontier(k=2) ⊇ {frontier(k=1) 的那个节点}`（因为 `k=2` 取前 2，第一名与 `k=1` 相同，
且同分按同一顺序）。归纳 ⇒ **`s1(k=2) ≥ s1(k=1)`，`s1(k=3) ≥ s1(k=2)`**。
⇒ 若出现 `s1(k=2) < s1(k=1)`，则是**装置 bug**，不是读数。这一条用来抓装置错误，不参与判决。

## §4 反证组（证明本条判据不是死代码）

- `k=1` 若**不再**停在 0.8（变成 8/8），说明「同分」根本没发生 ⇒ 本轮前提不成立，全部结论作废。
- `g7d2` 若**出现差异**，说明差异不是来自「并列候选」（该题无并列）⇒ W4 押破，且 W2 的归因要重写。
- `ON × k=2` 若仍是 4/8，说明「活盆被保留」不等于「能到 1.0」⇒ W2 押破，**「tie-break 是唯一卡点」判破**。
