# V131 结果：让系统自己检查「我写下的键有没有可能被匹配到」

跑前预注册：`PREREG.md`（2026-11-15 16:17 落盘，**先写后跑**）。
装置：`v131.py`，零模型、零网络、零子进程。耗时 2 分 24 秒。

## 一、装置要点

用 monkeypatch 拦住 `v121.gen` 当**旁观者**：生成照常，只把每个候选的 `abstract()` 记进
`REACH[(tid,h)]`。⛔ 搜索器一字未改。

于是自检的边际成本 = **0 次判分**（候选本来就要生成），且**不读分数、不读 test、不读人写的规则**。

- `SELF`：`reach` = 搜索中**全部**生成过的候选（深度 1~6）
- `NAIVE`：`reach` = 只算从**基线代码**生成的那一批（深度 1）
- `INV`：判据**反过来**（判死可匹配的、判活不可匹配的）

## 四、W4 押破的机制（本轮最重要的读数）

```
|all| != |d1| 的实现数 = 0        ← 25 个实现，逐实现相同
```

我押的是「生效动作可能在深度 ≥2 才出现，所以只看深度 1 会误杀」。
**实测：深度对「键的可达性」没有增量。**

机制一句话：**`abstract()` 把「在哪个节点上改」抹掉了，只留下「怎么改」。**
同一个抽象动作可以在很多不同节点上施加，而深度 1 从基线节点施加时就已经产生了这个键。
⇒ 「深层才可达的键」在抽象层面几乎不存在。

⭐ 这条反过来印证了 V121 的机制：记忆的价值 ∝ 候选空间大小 —— 因为**抽象键在多个深度重复出现**，
所以一条键能覆盖的候选比它的来源节点多得多。

⛔ 不许改口说「本来就该用深度 1」：押破就是押破，`NAIVE` 之所以没掉分是**结果**，
不是我事前的理由。

## 五、判决：自省从「半」到「第一格闭合」

✅ **系统自己检查了自己的输出，并且给出与人写规则完全相同的集合（差集 0）。**
V130 那条规则（`!= ('?','<baseline>')`）是我读过 `abstract()` 兜底分支才写下的；
本轮系统在**不知道那条规则存在**的情况下，用「这个键在不在我生成过的候选里」推出了同一个集合。

关键：**这个判断不需要分数、不需要 test、不需要人**，边际成本 0 次判分。

## 六、边界（⛔ 跑前已写死，不许扩口径）

1. **抓不到冗余**：4 条 `('T2',"'on'")` 是**可匹配**的键，自检一定判活，实测也确实判活。
   ⛔ 不许把「删掉不可匹配」说成「系统学会了裁剪记忆」—— 它只回答「这条键有没有可能被用到」。
2. **不判断对错**：可匹配 ≠ 有用。V128 已证「可匹配且边际 0」存在。
3. **不发明目标**：它检查的是**人给的动作空间**里生成的候选。动作空间仍是人写的，V79 那堵墙一字未碰。
4. **只在一个库**（25 实现 / 4 题）上验证。
