# V145 预注册：让复核本身有成本

> 落盘时刻 = 2026-11-16 14:30，**在任何代码改动之前**。纪律 1。

## 0. 上一轮登记的方案，以及我对它的第一处修正

§211.7 登记的是：

> 能不能只重算**结论依赖的那几条明细**（增量重算），并且证明「少算的那部分不影响结论」。

⛔ **这个方案对 `mean` 不适用，我撤回它的一半。** 理由是结构性的，不是实现细节：

    重算值 = fold(fold(score_r) / n_tasks) ，r 取遍所有轮
    ⇒ 任意一条明细的 score 改变，重算值就改变。

V144 的 J3 已经量到这一点（改一个 score ⇒ Δ=1.000e-03）。所以**「只重算结论依赖的那几条明细」
在数学上做不到** —— 结论依赖全部明细。可以增量的不是「算哪些明细」，而是
**「解析哪些行」**。这是本轮真正要回答的问题。

⇒ 本轮把「增量重算」改成「**按行局部化**」：审计一条记录，只需要那一行。

## 1. 问题

`ledger_audit(path, run_id)` 现在的实现在 `mw/bench.py:1340`：

    recs = _read_records(path)          # 整份账本 json.loads 一遍
    for rec in reversed(recs): ...      # 才按 run_id 找

`_read_records`（`mw/bench.py:1086`）逐行 `json.loads`，**任何一行坏 ⇒ 整份返回 `None`**。
真实账本 145 行 / 482 KB。

两个后果，都要用读数说话：

- **成本**：审一行要解析整份账本 ⇒ 随账本变长，复核变慢。
- **脆弱**：一行坏 JSON ⇒ 所有记录的审计都变 `UNVERIFIABLE`（按文件粒度 fail-closed）。

脆弱那条尤其危险：它看起来最保守，但账本越长、坏一行越可能，**复核可用性**就越低；
而一个永远给不出结论的闸，最后会被绕过（纪律 62 的同一形态，只是粒度从「每个闸」变成「整份文件」）。

## 2. 先量，后改

按 §211.7 的要求：先量出重算耗时随行数怎么涨，再决定增量是否值得。

**耗时分解**（真实账本 145 行，重复取中位数）：
- `read`：`path.read_text()`
- `parse`：逐行 `json.loads`（含 `strip`/空行跳过）
- `locate`：按 `run_id` 找目标行
- `arith`：`audit_measurement(hit)`（含 `recompute_mean` 与 R1~R6）

**规模曲线**：把真实账本按整行复制成 N = 145, 290, 580, 1450, 2900, 5800 行
（⛔ **合成数据，不是真实读数**；只用来量曲线，绝不用来报「真实账本多快」）。
每条曲线都标清 N 与总字节。

## 3. 押注（只押结构性命题）

| 编号 | 命题 | 押 |
|---|---|---|
| J0 | `mean` 依赖全部明细 ⇒ 「只算依赖的几条」不成立 | 删任意一条 ⇒ 重算值改变（V144 J3 已量） |
| J1 | 耗时分解里 **`parse` > `arith`** | 押成立（解析被解析的东西比加 6 个数贵） |
| J2 | 行局部化路径与整份路径在**干净账本**上逐格相同 | 押 **145/145**（状态 + 理由字符串**逐字**相同） |
| J3 | 行局部化**仍是 O(N)** | 押「是」—— ⛔ 不许用「快了几倍」掩盖「阶没变」 |
| J4 | 坏行隔离：非目标行坏 ⇒ 目标行仍可审 | 押 **行为分叉**：旧 UNVERIFIABLE / 新 VERIFIED + `bad_lines=1` |
| J5 | 目标行自己坏 ⇒ 必须 UNVERIFIABLE | 押成立（⛔ 不许因为别的行好而放行） |
| J6 | 预筛（原始行子串匹配再 `json.loads`）**只会多选不会漏选** | 押成立；但 **`run_id` 含 JSON 需转义字符时会漏** ⇒ 必须 guard |

**J6 的机制**：目标行必然含自己的 `run_id` 字面量 ⇒ 子串匹配不会漏。**除非**该字符在
JSON 里被转义（`"` → `\"`、非 ASCII → `\uXXXX`），那时原始行里没有那个字面量子串。
`run_id` 现由 `f"{os.getpid()}@{int(time.time())}"` 生成（ASCII 安全），但账本是**可手改的活文件**
⇒ 不能靠「现状安全」当证明，必须有运行时 guard。

## 4. 决策规则（**跑之前**写死，事后不许改口）

| 行局部化让「一行坏 ⇒ 全账本不可复核」恶化 | 整轮回退 |

## 6b. ⚠️ 跑前修正（探针之后、**改码之前**，2026-11-16 14:52）

**修正内容**：作用域从 `ledger_audit` 扩到 `ledger_verdict`（同一形状、同一处 `_read_records`）。

**为什么必须扩**：`run.py:1981` 与 `:2722` 先调 `ledger_verdict` 再调 `ledger_audit`。
只把审计改成行局部，**结论那一侧仍然整份解析** ⇒ 一行坏 JSON 就让 `ledger_verdict` 返回
`UNKNOWN` ⇒ 溯源闸照样拒 ⇒ **端到端的脆弱性一点没修**。
只改一半，读数会显示「审计能扛」，而系统其实还是死的 —— 那是假绿。

**给 `ledger_verdict` 加的判据**（与 J2/J4/J5 同构，编号加 `b`）：

| 编号 | 命题 | 押 |
|---|---|---|
| J2b | 干净账本上，新的 `ledger_verdict` 与原版**逐格相同**（状态 + 理由逐字） | 145/145 |
| J4b | 非目标行坏 ⇒ 目标行结论**仍可读** | 旧 UNKNOWN / 新正常 |
| J5b | 目标行自己坏 ⇒ **必须 UNKNOWN**（⛔ 不许因为别的行好而放行） | 成立 |

**扩作用域不放宽的东西**：`ledger_strata` / `ledger_audit_strata` 是**整份**诊断，
必须继续全解析并**报出坏行数**（`bad_lines`）。二者的分工正是本轮的核心：

- `ledger_audit` / `ledger_verdict` —— 回答「**这一行**」，可以跳过别的行；
- `ledger_*_strata` —— 回答「**整份账本**」，一行都不许跳。

⛔ 预筛省掉的不是「算」，是「**知道别的行坏没坏**」。所以跳过的行**不许**计入任何
「坏行数」——缺席不许冒充零（纪律 8）。字段名必须写成 `scanned` / `bad_in_scanned`。

## 7. 边界（⛔ 现在就写死，防止事后吹）
