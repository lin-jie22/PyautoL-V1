# RESULTS — V150「一条知识的单位是键，还是具体编辑」

## 0. 一句话

**「一条知识」在表示层不是一条。** 73.1% 的键抽象了 **≥2 个具体编辑**（d=1 闭包，零判分可证，
压缩比 2.07:1）；到了判分口径更糟 —— 同一个键在**同一个实现**上被判过的实例里，
**17/33 格的 `MAX` 说 VALID、`MIN` 说 INVALID**。
⇒ 三值不是知识的属性，是**（键，实例集，聚合方式）**的属性。这不是实现缺陷，是**表示缺陷**。

## 1. 装置

| 臂 | `s0>=1.0` 短路 | 一到 1.0 就 return | `n_eval` | 到 1.0 | 角色 |
|---|---|---|---|---|---|
| `ASK` | 关 | 关 | **2710** | 21/25 | 主臂（实例覆盖最全），= V149 |
| `ASK_EARLY` | 关 | **开** | **609** | 21/25 | 量「预算能截断几个实例」，= V149 |

`search_trace` 相对 V149 **只加一处**：事件里记 `src`（被判的具体源码）。
其余逐行不动。自校验：`2710/21`、`609/21`、基线实现 10/25、`universe_real=35`、基线格 16 —— **五项全部逐字复现**。
另：33 个有判分的格里，**事件数 == 去重源码数**（33/33）⇒ 下文的"实例数"不是重复判分虚增的。

## 2. 结构读数（零判分，`probe_mult.py` 与 `v150.py §1` 两次独立算出同一组数）

| 量 | 值 |
|---|---|
| d=1 键-格（25 实现） | **528** |
| d=1 实例（键×源码 对） | **1093** |

3 个 d=2 源码、最终判到 **8 个**。**键是索引，不是单位。**

## 3. 判分口径：实例比闭包更多（⛔ 这里押破了）

| 量 | 值 |
|---|---|
| 有判分的格 | 33 / 35（2 个 UNTRIED = V148 的两个硬墙） |
| 判分口径「≥2 个实例」 | **20** |
| d=1 闭包口径「≥2 个实例」 | **19** |
| 判到的实例总数 | **110** |
| 同批格子在 d=1 闭包里的实例数 | **52** |
| **判到但不在 d=1 闭包里的实例** | **60 / 110 = 54.5%** |
| 判分实例全在 d=1 闭包内的格 | **19 / 33** |

预注册 W3 押「判到的是闭包子集 ⇒ 判决口径的多实例格 **<** 闭包口径」。
**实测 20 > 19，且 60/110 个实例根本不在 d=1 闭包里。** 成因（§2b 诊断）：
`search` 会对 **frontier 上的新代码**再跑一次 `gen`，同一个键在新代码上产出**新的具体源码**；
V148 已经量过「d=2 给已有键新增 79644 个实例、0 个新键」，我没把这条接上。

⇒ **一个键的实例集不是闭包的函数，是搜索深度的函数** —— 这比"判到的是子集"更糟：
**分母本身没有上界。**

## 4. ⭐ 三个聚合给出三套结论（同一批证据）

| 聚合 | VALID | INVALID | UNTRIED |
|---|---|---|---|
| `MAX` | **26** | 7 | 2 |
| `FIRST` | **10** | 23 | 2 |
| `MIN` | **9** | 24 | 2 |

- `MAX ≠ FIRST`：**16 格**｜`MAX ≠ MIN`：**17 格**｜`MAX=VALID` 且 `MIN=INVALID`：**17 格（17/33 = 51.5%）**
- 换一个聚合，同一份判分从「26 条知识管用」变成「9 条管用」，跨度 **17 格**。

最干净的两个例子（`g7e2_truncate_tail`，同一个键、同一个实现）：

```
8184ec4d  S = [1.00, 0.00, 0.80]   MAX=VALID  FIRST=VALID  MIN=INVALID
bc8c4b09  S = [0.00, 1.00, 0.80]   MAX=VALID  FIRST=INVALID MIN=INVALID
```

两个实现的实例**得分集合相同**（只是顺序不同），`MAX`/`MIN` 完全一致，`FIRST` 却相反 ——
**`FIRST` 量的是搜索顺序，不是知识。**

## 5. ⛔ `MEAN` 不是第三个读数

阈值仍是 1.0，分数 ∈ [0,1] ⇒ `mean(S) >= 1.0 ⟺ min(S) >= 1.0`。
三聚合里只有**两个**独立读数（MAX / MIN），加上顺序敏感的 FIRST 是三个。
「取平均」不能救 —— 这条要写明，免得被当成第四种方案。

## 6. 预算把 `MAX` 与 `MIN` 往两个方向推

同一 35 格，只换预算（`ASK` 2710 → `ASK_EARLY` 609，早停截断 **18 格**实例）：

| 聚合 | `ASK`(2710) VALID | `ASK_EARLY`(609) VALID | 差 |
|---|---|---|---|
| `MAX` | 26 | **16** | **−10** |
| `FIRST` | 10 | 8 | −2 |
| `MIN` | 9 | 8 | −1 |

三值不同的格 = **10**（含 2 格 `VALID → UNTRIED`：那个 1.0 的实例根本没被排到）。
⇒ `MAX` 是预算的**单调不减**函数（实例越多越容易碰到 1.0），`MIN` 是单调不增。
**「MAX 说 VALID」在固定预算下不可证伪** —— 你没法区分「真的存在」与「还没试到」。

## 9. 结论

| 问 | 答 |
|---|---|
| 一个键对应几个具体编辑 | d=1 平均 **2.07** 个，最多 3 个；73.1% 的键 ≥2 个 |
| 判分时一个键会被判几次 | 最多 **8** 次（`g7e1` 的 `('T2', "'on'")`），且 **54.5% 的实例来自 d≥2** |
| 「这条知识对不对」有唯一答案吗 | **没有**：17/33 格同时可以是 VALID（MAX）和 INVALID（MIN） |
| 单位应该是什么 | **具体编辑**；键只是索引 |
| 拿它记三值要带什么 | **（聚合方式，预算，实例数）** —— 否则同一个格能给出相反结论 |

⛔ **不是「系统学会了判断知识对错」**：本轮零记忆写入、零决策改变，全部读数来自同一个
`v119.ev` 的重复调用；`MAX` 的读数还被证明随预算单调上涨、在固定预算下不可证伪。

## 10. 下一刀

V151：**`MAX` 这个读数能不能被证伪。** 既然 MAX 随预算单调不减、且实例集无上界，
「这条知识存在一个能到 1.0 的实例」就可能是**任何有限预算下都成立**的同义反复。
做法：把同一批格子的预算继续加（`MAX_ROUNDS` 6 → 更大），量
①`MAX=VALID` 的格数是否**还有增长**、②有没有饱和点、③若没有饱和点，
「按键记 VALID」就只能写成**带预算的下界**（"在 N 次判分内见过 1.0"），不能写成属性。
