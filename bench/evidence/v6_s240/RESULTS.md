# V151 结果：那把刀砍空了 —— `MAX` 能被证伪，但只在「覆盖到哪」这个前提下

**证据目录**：`bench/evidence/v6_s240/`
**读数**：`READINGS.txt`（最终）、`READINGS_v1_prints.txt`（只加打印行之前的同一份）、
`READINGS_v2_ceiling.txt`（**含我自己的「C 是上界」错误结论**，原样保留）、`readings.json`
**预注册**：`PREREG.md`（19:45 落盘，第一次判分之前）

## 0. 一句话

§217.8 登记的那把刀（`MAX_ROUNDS` 6 → 40）**从来没被用到**：25/25 实现在 `pool` 空时早就退出，
深度最大 2。改用满 d=2 闭包把覆盖推到 **28.6 倍**后，`MAX=VALID` 从 **26 → 28**，
`MIN=VALID` 从 **9 → 0** ⇒ **两个极值都在向自己的极端饱和**，而「同时两头」的格从 **17 升到 28**。
**`MAX` 不是同义反复**：5 个格有 6~12 个实例、最高分只有 0.00/0.20/0.60，且对它们的**全部**实例
各再展开一层（100% 覆盖）仍不翻。但**不能说「永远到不了」**：实例集无上界，且 C 连 A 的超集都不是。

## 2. §217.8 那把刀：6 轮与 40 轮**逐事件相同**

```
A 与 A_R40 事件序列逐格相同 = 25/25      n_eval 2710 == 2710
A 的「pool 非空的最大轮」分布 = {0: 13, 1: 8, 2: 4}     ← 最大值 2
```

⇒ `MAX_ROUNDS=6` 是个**死旋钮**：搜索在 `if not pool: break` 处就退出了，`pool` 需要「严格提分」的
子代，而分数阶梯有限、`visited` 又累积，两轮就没人能再提分。
**这个发现本身是跑前量测得到的**（PREREG §1 P1 已披露），不是判据读数。

## 3. 覆盖推上去之后（C 臂）

| 口径 | 实例（35 格） | `MAX`=VALID | `MIN`=VALID | 同时 `MAX`=VALID 且 `MIN`=INVALID |
|---|---|---|---|---|
| `A_DEPLOY` | 110 | 26 | 9 | **17** |
| `B_WIDE` | 158 | 26 | 9 | **17** |
| `C_FULL` | **3142（×28.6）** | **28** | **0** | **28 / 33** |

- **`MAX` 动 +2，`MIN` 动 −9。** 极值不是稳定量：一个往上爬、一个落到底。
- **`B_WIDE` 与 `A` 的三值完全一致（0 格翻转）**，实例 110→158 ⇒ **加宽 frontier 一个三值都买不到**。
- C 的每格实例数：min 0｜**median 12**｜max 233｜**20/35 格的实例数 < 20**。
  ⇒ 「×28.6 覆盖」是**极度不均衡**的，不能理解成「每格几千个实例」。

### 3.1 翻转的只有 2 格，而且正好是 V149 的那两条「负证据」

| 实现 | 键 | A 实例/三值 | C 实例/三值 | C MAX |
|---|---|---|---|---|
| `g7e2_truncate_tail::697caecc` | `('C1', "'…' + s[-n:]")` | **1** / INVALID | **11** / VALID | 1.00 |
| `g7e2_truncate_tail::c21ee3b8` | `('C1', "'…' + s[-n:]")` | **1** / INVALID | **11** / VALID | 1.00 |

交叉表（目标正确性 × 知识三值）：

```
A_DEPLOY: 待修 14/5/0｜已正确 12/2/2
C_FULL  : 待修 14/5/0｜已正确 14/0/2      ← 已正确 × INVALID 从 2 变 0
```

⇒ **V149 §216.3 的「唯一 2 条负证据」是覆盖 = 1 的产物**（补 10 个实例就都到 1.00）。
V149「两轴不可互推」的结论不变（四格仍全非空：14/5/0 与 14/0/2），但**证据要换**。

## 4. ⭐ `MAX` 到底能不能被证伪

**能。** 5 个格在 C 臂里有实例、且最高分到不了 1.0：

| 实现 | 键 | C 实例 | max | 分数分布 | B 臂（宽搜索） |
|---|---|---|---|---|---|
| `g7d2::480ada8e` | `('key', '.strip()')` | 5 | 0.20 | {0.0:4, 0.2:1} | 1 个实例，max 0.20 |
| `g7d3::0a6acc93` | `('ret', ".replace(',',' ')")` | 12 | 0.00 | {0.0:12} | 1 个，0.00 |
| `g7d3::17747356` | 同上 | 6 | 0.00 | {0.0:6} | 1 个，0.00 |
| `g7d3::5755e033` | 同上 | 7 | 0.60 | {0.0:1, 0.6:6} | 1 个，0.60 |
| `g7d3::8c8ac7f0` | 同上 | 8 | 0.60 | {0.0:1, 0.6:7} | 3 个，0.60 |

**d=3 探针**（每格取全部 C 实例源码再展开一轮 `gen`，`D3_CAP=40` 从未触顶）：

```
5/5、12/12、6/6、7/7、8/8 个父源码  ⇒  子代同键源码 0、12、6、7、8 个
最高分仍为 nan、0.00、0.00、0.60、0.60     ← 一格都没翻
```

⇒ 这些不是「还没试到」：**实例全看了，再深一层也看了，还是到不了 1.0**。
**`MAX=VALID` 是可证伪的**，反例就是这 5 个格（外加 2 个「一个实例都没有」的格）。

**但**：反例只能写成「在覆盖 C 下」——因为 C 连 A 的超集都不是（见 §5.3），
而实例集没有上界（V150 已量：54.5% 的判分实例来自 d≥2）。跨出覆盖点，负命题不可判。

## 5. 自踩四处

### 5.1 登记的那把刀是死的（§217.8 整个作废）

写预注册前先量了一次 `MAX_ROUNDS`：25/25 深度 ≤2、6 轮与 40 轮逐事件相同。
如果没有这次量测，我会花一整轮证明「加大轮数没用但不知道为什么」，然后错误地把结论写成
「MAX 与预算无关」。**真正无关的不是预算，是这个旋钮根本不在通路上**。

### 5.2 ⛔ W3 押破：押 33，实到 28

机制错在我把「8 万个实例对」当成了「每格几千个实例」。实际 35 格只分到 3142 个，
**中位数 12**，那 5 个负例格只有 5~12 个。⇒ **覆盖面不是均匀放大**，总数 ×28.6 掩盖了
「大多数格的实例数仍是个位数」。这与纪律 46（分母不同不许比大小）同型：
我拿全库的实例对当分母，去推每格的期望。

### 5.3 ⛔ 「C 是这一类搜索的上界」是错的，判据自己抓住了

预注册把 C 定义成「≤2 轮 gen 的上界」。跑后对照：`B_WIDE` 的 4094 个事件里
**1296 个（31.7%）落在 C 之外**。

成因（口径错）：`depth` 只记 `pool` **非空**的最大轮，而**空池的那一轮仍会把候选判一遍**
⇒ 部署搜索实际评估到「下探深度 + 1」层的源码。C 只做了两轮 `gen`，罩不住第三层的评估。
⇒ **C 是覆盖率上的一个点，不是上界。** 本轮的「任何预算都推不动」一类说法全部删掉。
含这个错误结论的读数原样留 `READINGS_v2_ceiling.txt`。

### 5.4 装置崩：把分数当源码喂给 `gen`

d=3 探针里写成 `r["sc_c"]`（分数列表）而不是 `r["src_c"]`（源码列表）⇒
`compile() arg 1 must be a string`。崩在读判据之前（`readings.json` 未落盘），修后重跑。
⛔ 记一笔：**表里同名的两个字段只差一个字母**，这种崩只有在真跑时才看得见。

另：打印口径也修过一次 —— 「待判源码」原本按实现求和（39260），而 CACHE 键是 `(tid, code)`，
实际判分 **39072** 次。两个数都报，别混。

## 7. 结论

| 问 | 答 |
|---|---|
| §217.8 那把刀 | **砍空**：`MAX_ROUNDS` 从不是约束（深度 ≤2，6==40 逐事件相同） |
| `MAX` 能证伪吗 | **能**：5 个格有实例、max ≤0.60，实例全看、再深一层也不翻 |
| 能说「永远到不了」吗 | **不能**：实例集无上界，且 C 不是 A 的超集（1296/4094 在 C 外）⇒ 只能写「在覆盖 C 下」 |
| `MAX` 与 `MIN` 谁稳 | **都不稳**：最高分随覆盖 26→28，最低分 9→0；「同时两头」17→28 |
| 加宽搜索有用吗 | **没有**：`B_WIDE` 实例 +48（110→158），三值翻转 **0** 格 |
| 那 V150 的三聚合呢 | 26/10/9 只在 **110 个实例**的覆盖下成立；C 上 MAX 28、MIN 0。**三聚合的差距随覆盖单调扩大**，不是收敛 |

⛔ **不是「系统学会了判断知识对错」**：零记忆写入、零决策改变；`MIN` 在 C 上完全饱和（0/35），
说明「这条键好不好」在最细覆盖下对**每一条**键都有两个相反答案 —— 键粒度上根本没有唯一答案。

## 8. 边界

1. 语料仍 25 实现 / 4 题；`MAX_ROUNDS`、k=2、`order_key`、`abstract()` 键形状全是人定的。
2. C 是「两轮 `gen`」的闭包，**不是**全编辑空间；d≥3 只对 5 个负例格做了全实例展开（不是对 35 格）。
3. 5 个负例格的「到不了 1.0」是**分数层面**的事实（`v119.ev` 的用例通过率），不是「这条编辑在语义上无意义」。
4. ⛔ 不碰 V79（自造判据 0/8）。
5. `B_WIDE` 是反事实臂，不是部署建议。
